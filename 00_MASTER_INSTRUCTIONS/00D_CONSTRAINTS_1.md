## CONSTRAINTS (Quick Reference)
 
1. NEVER modify writer **wording** (trust the content source — PageForge `.txt`, raw Writers Template `.docx`, or MTK `.docx` — as-is). The permitted changes are documented *casing/format* normalisations that leave wording untouched: lesson-menu label & list-item casing (constraint 24) and a **multi-word ALL-CAPS header title → sentence case** (see `01` → Title casing — single all-caps tokens, proper nouns and acronyms are preserved or red-flagged, never blindly lowercased) — **plus one documented removal: emoji (constraint 74)**, the sole case in which the Convertor deletes writer characters rather than re-casing them. Emoji are stripped (ticks and crosses excepted), the surrounding **wording is untouched**, and the removal is **disclosed** with a visible `Red Flag:` note — never silently. Nothing else is ever added, reworded, corrected, or removed: typos, grammar, and formatting inconsistencies all stand.
2. NEVER add inline CSS, JavaScript, or uninventoried code. (Documented exceptions only: the `<p style="color: red; font-weight: bold;">` red-flag / designer-note style; and — for BLL-series modules — the `style="text-transform: lowercase"` on the header title `<span>` — see `01_PIPELINE_EXTRACTION_TAGS.md` → Template Title Patterns.)
3. NEVER invent CSS classes or HTML structures
4. NEVER hide student content exclusively in HTML comments; NEVER use comments to pass designer-facing notes or interactive answers — use visible red flags (see constraint 37)
5. NEVER render square-bracket tags as visible text
6. NEVER guess interactive structure — red flag + visible fallback
7. NEVER add `<span>` wrappers to body headings (`<h2>`–`<h5>`) — spans are ONLY for `<h1>` header titles
8. ALWAYS match opening/closing div tags
9. ALWAYS use row/col grid for body content
10. ALWAYS derive skeleton from provided structural reference (dedicated template OR reference module files)
11. ALWAYS consult component sections before writing interactive HTML
12. ALWAYS apply Page Boundary Validation Rules
13. ALWAYS normalize tags before mapping
14. Writer's tag determines component selection (not table headers)
15. `noShuffle` only when writer explicitly requested
16. Lesson pages: zero-padded lesson number (e.g., `01`, `02`) in `#module-code`; module title (not lesson-specific title) in `<h1><span>`; first "Lesson N" H2 rendered as body `<h3>` (not consumed into header)
17. Wide interactives (D&D column) use `col-md-12 col-12` outer wrappers; a D&D column with many images uses `col-12` (Standard) / `col-md-11 col-12` (Inquiry & Fundamentals) — **never** `col-md-10` (see constraint 56). ALL carousel types (image, video, and external nav button) use `col-md-8 col-12` for the viewer
18. `[rotating banner]` maps to `rotateBanner` component, NOT carousel
19. When using reference module files (Mode B), ALWAYS replace ALL reference module codes and titles with the new module's code and titles — never leave stale references
20. When using reference module files (Mode B), ALWAYS consult `06_TEMPLATE_RECOGNITION.md` to classify, validate, and check for known pitfalls BEFORE deriving the skeleton
21. When using reference module files (Mode B), ALWAYS set `template` attribute to match the new module's year level — do NOT copy from reference if mismatched
22. When using reference module files (Mode B), do NOT carry over custom CSS links or stickyNav.js from reference — these are module-specific
23. Lesson page module menus use `<h5>` label headings normalised to standard patterns (e.g., `<h5>We are learning:</h5>` + `<h5>I can:</h5>`) — NOT writer's verbatim text, NOT `<h4>` headings, NOT intermediate `<p>` elements
24. Module menu list items: no italic wrapping, lowercase start, verb form matching heading context
25. Years 9–10 / NCEA lesson pages: include dual `<h1><span>` titles (English + Te Reo, module-level) on EVERY lesson page
26. D&D standard with `images` class: text in `questionContainer` (col-7), images in `dragContainer` (col-5) — NEVER images in questionContainer
27. DropQuiz standalone Q&A pairs: use list layout (no `layout` attribute, `<ol><li>` with row columns) — NOT paragraph layout
28. Use lowercase `<!doctype html>` and XHTML-style self-closing tags on void elements
29. Single-character speech bubbles: use `bubble-basic` + positional class from writer template layout (`bubble-left`/`bubble-right`/`bubble-top`/`bubble-bottom`); writer CS positional instructions override default layout; multi-paragraph content needs wrapping `<div>` inside bubble; image column needs `paddingL`/`paddingR` in horizontal layouts
30. ALWAYS prompt the user for image output mode (Placeholder or Direct Link) if they have not stated a preference — do NOT silently default to either mode
31. In Direct Link Mode (Mode D), emit clean `<img>` tags with no HTML comment blocks — the actual filename in `src` is sufficient; comment blocks are only used in Placeholder Mode (Mode P)
32. Apply the chosen image output mode uniformly to ALL images in the conversion — do NOT mix modes within a single output file
33. **ACKNOWLEDGEMENTS ALWAYS GO AT THE BOTTOM OF THE FIRST PAGE (lesson 0.0 / the `-00` overview page)** — placed after the footer using the accordion structure. NEVER place acknowledgements on the last page or any other lesson page. This applies to ALL conversions (PageForge, standard `.docx`, and MTK).
34. The content source may be a PageForge `.txt`, a raw Writers Template `.docx`, OR an MTK `.docx`. When a raw (non-MTK) Writers Template `.docx` is supplied, convert ONLY the relevant student-facing content (everything from the first `[TITLE BAR]` onward) — IGNORE all front-matter (submission checklist, LOT tags table, Section A — Merging Resources, Section B guidance box, contents page, sign-off line)
35. A Media List `.docx` may be OPTIONALLY supplied alongside the content source — use it to verify external media links and to source accurate media titles/descriptions for the acknowledgements; it never supplies student content and never changes page boundaries
36. For ALL graded MCQs the component is the `multiChoiceQuiz` class family (`mcqQuestion` / `mcqQuestionText` / `mcqOptions` / `mcqOption`) — NEVER the legacy `multiQuiz` (`mQContainer`/`mQOption`/`.answer`). This includes **single-answer / two-option** graded questions (e.g. "Is this a plant cell or an animal cell?"): the correct option carries `value="correct"` and wrong options carry no `value`. Graded **multi-select** quizzes additionally use the `mcqSomeSelected` modifier on the container. Do NOT use the `checkAll` self-assessment variant for a graded quiz, and do NOT leave a typed question number inside `mcqQuestionText`. See COMP_02
37. NEVER emit an HTML comment that discloses an interactive's correct answer(s) or answer key — answers live only in the functional markup attributes the engine requires. Designer-facing notes, CS instructions, ambiguities, writer design directions, and deferred developer actions are rendered as VISIBLE red flags — prefixed by source (`Note from {author}:` for a captured reviewer comment, `Writers Note:` for the writer's own note/instruction, `Red Flag:` for an issue the Convertor detects, `Designer/Developer To Do:` for a deferred asset/URL/setup the developer must supply during production) and rendered red **and bold** (`<p style="color: red; font-weight: bold;">Red Flag: ...</p>`), not hidden comments. The only retained comment uses are the Mode P commented-out image reference, the MTK `<!-- CS: Item N -->` media-catalogue annotation, the `<!-- &amp;start=0 --> <!-- &amp;end=0 -->` time-parameter placeholders inside the Creative-Services Vimeo scaffold (constraint 64), the acknowledgements page-label annotation `<!-- Lesson N.N -->` (constraint 73 — a structural grouping label on each media-carrying `acksLesson` div), and — **only in Split Mode (Mode 5) output** — the `PAGEFORGE-GUIDE-START` … `PAGEFORGE-GUIDE-END` manual-stitch guidance blocks (highly detailed instructions for a human developer stitching the files by hand; carry no student content, no designer-action notes, and no answers) together with the `PAGEFORGE-SPLICE` / `PAGEFORGE-SECTION` / `/PAGEFORGE-SECTION` structural splice markers (all machine tokens consumed and removed by PageForge's Page Stitcher; they never survive into the stitched/human-facing module and are not a communication channel). See `02_DATA_CONTENT_VERIFICATION.md` → Comment & Red Flag Policy and `13_SPLIT_MODE.md`
38. For the templates `refresh_template_0.0_1_template_ECH`, `refresh_template_0.0_2_template_1-3`, and `refresh_template_0.0_3_template_4-6`, AUTOMATICALLY apply the `autoCheck` attribute to every interactive that supports it — see `03_COMP_CORE_INTERACTIVES.md` COMP_00 (autoCheck Auto-Application)
39. A designer may request a ONE-OFF deviation from the documented patterns for a specific module or a few of its elements. Honour explicit one-off designer instructions for that module only — apply them as directed, do NOT treat them as a permanent rule change, and do NOT propagate them to other modules. Following an explicit instruction is not "inventing". One-off overrides still may not cross the absolute boundaries (no new framework CSS/JS, no editing student content). See `08_MODULE_SUPPORT_DEBUGGING.md` → One-Off Module Overrides
40. Comparison Mode is triggered by the phrase `COMPARISON MODE` plus uploaded finished HTML files. In Comparison Mode, never convert, never edit content, and **never regenerate the project files** — only analyse and produce **one downloadable difference report** containing **only knowledge-derived differences** (where the project's HTML was produced by a stored project-knowledge rule). Differences whose output was lifted or mirrored from the supplied structural reference, example module, or other templated file are **filtered out and never reported** (refining the project files cannot change what an external template ships). Differences are numbered in a single continuous sequence; the **five scope options are listed once at the top of the report** — (a) series + level (applies to `[PREFIX]` modules at `[LEVEL_DESCRIPTOR]` only, i.e. this subject series at this level — NOT other subjects at the same level), (b) module series (all `[PREFIX]` modules across every level), (c) universal, (d) ignore once, (e) ignore always — and are NOT repeated after each difference. **Phase 1** is a streamlined report (three sections per difference: raw content → originally generated code → designer's refined code; the "source of the project's output" is withheld). The designer then replies with `number-letter` pairings (e.g. `1-A, 2-C, 3-D`); Claude regenerates a **finalized detailed report** (Phase 2) where each included difference has four sections (adding the cited source rule — file/section/constraint) plus its chosen scope in full English. **(d) Ignore once differences are omitted entirely from the finalized report; (e) Ignore always differences are kept with an explicit instruction for a future, separate conversation to add them as a standing exclusion.** The project files are NOT regenerated inside Comparison Mode — the finalized report is the deliverable and is actioned later in **Update Mode** (`11_UPDATE_MODE.md`). `[LEVEL_DESCRIPTOR]` is resolved from the structural reference's `template` attribute on `<html>` (e.g. `Phase 2 (Years 4–6)` for `template="4-6"`); use the year range alone if no Phase number is documented for the level. Certain difference types are NEVER captured — red flags / designer notes, overview module-menu heading styling (one-source-of-truth WIP), and bespoke designer presentation decisions; see `09_COMPARISON_MODE.md` → Differences NOT to Capture (Exclusions). See `09_COMPARISON_MODE.md`
41. **(Universal)** A `<p>` whose sole purpose is to caption/describe an adjacent image carries `class="captionText"` — in every context (standalone, in columns, inside accordion content). Ordinary prose `<p>` stays unclassed. This is the plain caption-under-image case, distinct from the hover-overlay `captionImage` component. See `01_PIPELINE_EXTRACTION_TAGS.md` → Images (Caption text under an image)
42. **(Universal)** Numbered instructions/steps/sub-questions inside an activity or interactive use semantic `<ol><li>` (with `start="N"` for continuation across split content) — NEVER `<p>1. …</p>` manual numbering; and no typed leading number is left inside a quiz/MCQ question string. See `03_COMP_CORE_INTERACTIVES.md` → COMP_00 and `02_DATA_CONTENT_VERIFICATION.md` → Numbered Instructions in Activities
43. **(Universal)** Any activity that ends in a dropbox submission button ("Go to dropbox" / "Upload to dropbox" / `[trigger engagement]`) carries the `dropbox` modifier on the activity wrapper (`activity dropbox`, or `activity interactive dropbox`). Applies to ALL module series **except the BLL series**, which adds the dropbox button but does **not** append the `dropbox` modifier to the activity wrapper (BLL-scoped carve-out — see `14_SUBJECT_GLOBAL_PARAMETERS.md` §14.7). The carve-out is **BLL-only** and does **not** extend to the separate **BLLR** series. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Activities
44. **(Universal)** clickDrop `rel` is auto-calculated from document order — omit it by default. A single clickDrop pair never needs `rel`; only add `rel="N"` to override out-of-order multi-pair authoring. See `04_COMP_SEGMENTS_OVERLAYS.md` → Click Drop
45. **(Universal)** The acknowledgements wrapper is `<div class="acks acksTemplate">` (the `acksTemplate` modifier is standard); add `acksAI` as well — `<div class="acks acksTemplate acksAI">` — when the module uses AI-generated media. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Acknowledgements
46. **(Universal)** A clickable labelled DIAGRAM (labels that point to specific parts of an image and reveal text on click — cell/anatomical/equipment diagrams, map features) is built with `imageLabel` + `layout="labelLine"` using `<div class="label infoTrigger" … direction/top/left/pointTop/pointLeft><p>…</p></div>` children and `imgLabel` on the image — NOT `infoImage` with positioned `<span/p class="infoTrigger" style="top/left">`. Reserve `infoImage` for simple hotspot overlays with no leader lines. See `04_COMP_SEGMENTS_OVERLAYS.md` → Image Label / Info Trigger Image
47. **(Universal)** On a lesson page, drop a body heading whose text is identical (ignoring case/punctuation) to the `<h1>` header title — the module title already shows in the header, so the duplicate body `<h3>` is omitted and the first body `<p>` follows directly. A body heading introducing a *different* sub-topic is kept. See `01_PIPELINE_EXTRACTION_TAGS.md` → Headings
48. **(Universal)** Typing-quiz inputs use `placeholder="Type here"` (a visible prompt), not an empty `placeholder=""`. See `03_COMP_CORE_INTERACTIVES.md` → Typing Quiz
49. Update Mode is triggered by the phrase `UPDATE MODE`. It is the project's mechanism for **permanently changing its own stored instruction files**. The changes to action may be supplied in **any format** (a finalized Comparison Mode difference report, free-typed instructions, a bullet list, a single line, or an uploaded file) in the same or the next message. Update Mode normalises the input into discrete scoped changes (reusing `09`'s five-scope vocabulary: a/b/c propagate at increasing breadth; d = ignore once → no file edit; e = ignore always → add a standing exclusion to `09_COMPARISON_MODE.md` → Section 4.1), **checks each change against the change ledger `12_CHANGE_LEDGER.md` for conflicts** (a request that contradicts a `Locked` decision is BLOCKED and not actioned until the design authority unlocks it; a request that overturns a prior *unlocked* decision pauses for confirmation), **classifies each change Routine vs Major**, confirms scope and any guardrail-weakening change first, performs a **blast-radius sweep** to find EVERY affected file (owning rule + every cross-reference, constraint-list entry, index entry, ledger row, and project-instructions touchpoint), then **produces ONE Repo Update Brief** — a precisely-worded instruction block for a Claude Code session opened on the `htmlconvertor-kb` GitHub repository (where the knowledge files live as granular parts), which edits the exact part files in place, appends the drafted ledger row(s), runs the repo's checks, and commits; **Update Mode never regenerates or outputs project files** (`CL-0053`; see `11_UPDATE_MODE.md` → Section 10). A **report-vs-report conflict** (a change from a finalized difference report that clashes with a prior change also from a finalized difference report) is **catalogued for the team's design authority, Persephone, to resolve**; on resolution in favour of the change it becomes `Locked` (immutable), otherwise it is `Reverted`. Every **non-conflicting** change is actioned directly and recorded in the run's restated change list and per-change log — it is not sent for sign-off, and **no difference report is produced for the designer** (constraint 76). A clash with a `Locked` decision is still **blocked**, and a clash with a prior change that arrived by any non-report channel **pauses for the designer to confirm** rather than escalating. Update Mode targets the rule files ONLY — never student content, never converted HTML — never invents changes the designer did not request, and never overrides a lock without authority sign-off. It is the downstream actioning conversation `09` → Section 10 hands off to. See `11_UPDATE_MODE.md`
50. Every project-knowledge file (`00`–`14`) carries a **"Last updated" line as its first line** in the format `> **Last updated:** Weekday, Dth Month, YYYY h:MM AM/PM` (e.g. `Thursday, 18th June, 2026 4:39 PM` — full weekday, ordinal day, full month, 12-hour time with `AM`/`PM`, no leading zero on hour, New Zealand local). On every update in any mode (in Update Mode, done by the linked Claude Code session per the Repo Update Brief), refresh it to the current date/time — add it if absent, update in place if present (never stack two). It marks the last update, not original authorship. See `11_UPDATE_MODE.md` → Section 13 and `00` → File Timestamp Convention
51. The change ledger `12_CHANGE_LEDGER.md` (in the repository: the `12_CHANGE_LEDGER/` folder of parts) is the **in-house**, append-only **conflict & lock registry** — no external spreadsheet, export, or manual upkeep. It has three parts: **Part 1 Locked Decisions** (binding/immutable — the conflict check reads this first), **Part 2 Pending approval** (report-vs-report conflicts awaiting the design authority's resolution), and **Part 3 Change History** (full audit log). Update Mode reads it at the start of every run to check new changes for conflicts and locked decisions, and records outcomes by drafting the new row(s) into the Repo Update Brief for the linked Claude Code session to append to the latest history part (never regenerated in full). A change that contradicts a `Locked` entry is **blocked** (not actioned) until the design authority unlocks it; a `Locked` entry can only be changed after explicit authority sign-off to unlock. Keeping it in-house is feasible at any size because conversion chats never read it (only Update Mode does) and project knowledge is retrieved rather than bulk-loaded; only the compact Part 1 drives conflict-checking. See `11_UPDATE_MODE.md` → Sections 4, 6, 7 and `12_CHANGE_LEDGER.md`
52. **(Universal)** Image **`alt` text** is concise, descriptive, and **free of the phrases "image of", "picture of", and "stock photo"** (the words *stock photo* must never appear in any alt text). For an **iStock** image, the preferred alt value is the **iStock/Getty API image name** — the descriptive title carried in the supplied iStock acknowledgements file or recoverable from the iStock link (e.g. *"Confident boy sitting on bicycle in the forest"*) — used as the alt in both the Mode P commented-out reference and the Mode D live `<img>`. See `01_PIPELINE_EXTRACTION_TAGS.md` → Images (alt text)
53. **(Universal)** When a developer supplies an **iStock acknowledgements file** (a list of acks lines sourced directly from the iStock/Getty API), it is **authoritative and exact** for the iStock items it covers: those acks entries are inserted **verbatim** into the acknowledgements block in lesson order (overriding the asset-URL-slug title derivation for those items), and the descriptive image name in each line is the preferred alt text for the matching image. It supplies no student content and never changes page boundaries. See `01_PIPELINE_EXTRACTION_TAGS.md` → iStock Acknowledgements File and `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Acknowledgements (Sourcing)
54. **(Universal)** A **video / YouTube acknowledgement** entry uses the layout `<p>Video: [title], [author], <a href="[URL]" target="_blank">[URL]</a>, retrieved d/m/y. Used in online learning within the exception for education.</p>` — the URL is a live wrapped anchor, the **retrieved date is the date the conversion is processed** (today's date), and the permission string is the education-exception wording. The **video title is always the video's full published title** — never the Media List's writer-descriptive label (which is often abbreviated, wrong, or invented); if it cannot be confirmed, raise a visible red flag. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Acknowledgements (Entry format)
55. **(Universal)** A submission button that sends the student to the **dropbox** or to their **portfolio** keeps its full **"Go to"** label — **"Go to dropbox"** / **"Go to portfolio"** — the leading "Go to" is never dropped to a bare "Dropbox" / "Portfolio". (This is the button *label* convention; the `dropbox` activity-wrapper modifier of constraint 43 is separate and still applies.) **Series exception:** the **BLL, LS, and HPE** families label the dropbox button **"Upload to Dropbox"** — a series-scoped label that sits **alongside** (does not overturn) this universal "Go to …" default; see `14_SUBJECT_GLOBAL_PARAMETERS.md` §14.11. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Buttons
56. **(Universal)** **Activity/interactive wrappers never use `col-md-10`.** Every activity wrapper (`activity`, `activity interactive`, and the wide-interactive layouts — D&D column, mcq/radio quiz, flipCard, carousel, clickDrop, etc.) that needs more width than the default `col-md-8 col-12` takes one of three outer widths: **`col-12`** for Standard-family modules (the default), **`col-md-11 col-12`** for the Inquiry and Fundamentals sub-types (detected by the `inquiry container-fluid` / `fundamentals container-fluid` body class — see `06_TEMPLATE_RECOGNITION.md`), or **`col-md-8 col-12`** when the activity is paired with an `alertImage` — in which case the `alertImage` takes **`col-md-4`** (8 + 4 = 12) and this pairing width **overrides** the sub-type default (an Inquiry/Fundamentals activity paired with an alertImage is still `col-md-8`, not `col-md-11`, so the image has room). Radio-quiz option cells stay `col-md-1` inside their own inner rows and are **unaffected** by the wrapper change. This rule is **forward-only**: existing modules built with `col-md-10` activity wrappers are pre-rule and are NOT retro-flagged as violations. Plain, non-activity narrowed **content** blocks are outside this rule and may still use `col-md-10`. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Columns & Floating Columns and `02_DATA_CONTENT_VERIFICATION.md` → Interactive Wrapper Width
57. **(Universal)** A **captured whitelisted reviewer comment** — a red-text note PageForge re-emits from a writer `.docx`'s native Word margin comments, carrying a leading `Note from {author}:` lead where `{author}` is one of the six whitelisted reviewers (**Kate Scanlon, Nadia Stanton, Caroline Schwer, Simon Vita, Amanda Griffiths, Creative Services**) — is rendered as a **VISIBLE red designer message** in the finished HTML, using the established red **and bold** form (the canonical rendering is `<p style="color: red; font-weight: bold;">Note from {author}: {verbatim text}</p>`). PageForge supplies the `Note from {author}:` lead itself; emit it **verbatim** — never reword the lead, drop the author, substitute another prefix, paraphrase, summarise, or truncate the text. Render it **in position** (immediately before the element it refers to, mirroring where PageForge placed it); treat it as **designer-facing, never student content**, and **never relocate it into an HTML comment**; do **not** tag-parse a prose comment (the tag-only branch must not swallow it). The leading `Note from {author}:` lead is the **only** thing distinguishing a captured reviewer comment from a writer's own red-font note/instruction (which renders `Writers Note: …`) — keep the lead either way. Whitespace-only and tag-only red-text blocks behave exactly as before. This is an **extension of the existing Red Text Handling rule**, reliable, attributed, and intentional for this category. Applies to the PageForge `.txt` pathway (PageForge performs the whitelist + actionability capture). See `01_PIPELINE_EXTRACTION_TAGS.md` → Red Text Handling and `02_DATA_CONTENT_VERIFICATION.md` → Comment & Red Flag Policy (Captured Reviewer Comments)
