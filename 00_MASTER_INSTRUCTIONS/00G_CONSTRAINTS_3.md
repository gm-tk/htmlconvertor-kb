75. **(Universal)** **A STANDALONE `[external link]` builds an `externalButton`; an INLINE one stays an anchor — position decides, not the tag.** Writers use `[external link]` and `[external link button]` interchangeably, so the tag alone is not a reliable signal. A link the writer gave **its own line/paragraph** (a call to action) renders `<a href="URL" target="_blank"><div class="externalButton">Text</div></a>`; a link sitting **inside prose, a list item, or a table cell** renders a plain `<a href="URL" target="_blank">Text</a>`. `[external link button]` **always** renders as a button regardless of position. The `external link` / `external link button` **tag distinction is retained** in the taxonomy — it is the *rendering* of a standalone `[external link]` that now matches the button form. **The test:** would removing the link leave a grammatically incomplete sentence? If yes → inline anchor. Containment in an `alert`, accordion, or speech bubble does not change the test — the prose relationship decides. Borderline → render the **anchor** and raise a `Red Flag:`. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Buttons and `01_PIPELINE_EXTRACTION_TAGS.md` → Tag Taxonomy → Link/Button Tags
76. **(Universal — Update Mode)** **Update Mode NEVER produces a finalized difference report for the designer.** No Update Mode run generates, writes out, presents, or offers a difference report of its actioned changes for Gavin — regardless of the intake channel (finalized report, direct-typed, project instruction), the classification (Routine or Major), or the scope. The run's own output **is** the record: the restated/normalised change list, the conflict report, the Repo Update Brief (with its drafted `12_CHANGE_LEDGER` row(s)), and the per-change log. Do not offer to produce one, and do not close a run by reminding anyone to email one. **The Persephone conflict catalog is unaffected** — a report-vs-report conflict is a different artefact on a different path (`11` → Section 7.1) and is still produced whenever one occurs. Standing designer instruction of 16 July 2026 (ledger `CL-0052`), superseding the report-to-Gavin limb of `CL-0006`; the rest of `CL-0006` (Persephone engaged only for report-vs-report conflicts) stands. See `11_UPDATE_MODE.md` → Sections 7, 15, 16
77. **(Universal)** **A `col-md-8` column is never nested directly inside another `col-md-8` column.** Where a row inside a `col-md-8 col-12` wrapper needs a column, use `col-md-12 col-12` (or a documented inner pattern such as the `col-md-6` pair) — never a `col-8`-family class. A `col-md-8` inside a `col-md-12`, and a `col-md-12` inside a `col-md-8`, are both fine. Applies to inner activity columns (`col-8`) too. See `02_DATA_CONTENT_VERIFICATION.md` → Content Rules and `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Columns
78. **(Universal — Interactives Build Mode)** **Interactives Build Mode (Mode 6)** is entered by the phrase `INTERACTIVES MODE` **or** by the upload of a PageForge interactives worklist, which is self-identifying (header `INTERACTIVE REFERENCE — {CODE}` plus per-entry `REFERENCE CODE:` lines) — never to be confused with a content-source `.txt` (`--- CONTENT START ---` / `[TITLE BAR]` → Mode 1). It builds **only** the un-built interactives the worklist lists, as **anchored fragments** for PageForge's Page Stitcher: each build is wrapped in exactly `<section class="cv2-built" data-cv2-ref="{REFERENCE CODE}">`, the code copied **character-for-character**, **once**, never renumbered, re-ordered, abbreviated or nested. A worklist whose entries carry **no** reference codes is **not built** — the developer is asked to re-convert with the current HTML Generator. The fragment **starts at the widget's own wrapper**: the generated page already supplies the activity box, the row/column grid, the headings and the surrounding prose, so the mode never emits pages, menus, headers, footers, acknowledgements, activity boxes, `<html>/<head>/<body>`, or a `<script>` head include (the Stitcher injects the two `crossword`/`wordFind` includes itself). Output is complete downloadable file(s) — `{CODE}_interactives_built.html`, or batches of **up to 8** builds (`_1of3.html`, `_2of3.html`, …) emitted **one file per response** after an announced plan, every code in exactly one file. The **component files remain the markup authority** (`03`/`04`/`05` COMP sections, `02` Section 06 for data patterns, `14` for family conventions) and **every hard constraint still applies** — including constraint 1 (writer content verbatim), 2 (no invented classes/CSS/JS), 3 (no visible tags), 4 (never guess a structure — closest documented pattern plus a visible note) and 5 (nothing buried in a comment). Where a worklist entry carries **two or more task interactives**, the fragment cannot split the page's activity box: build them all in `Content:` order inside the one section and add ONE visible `Designer/Developer To Do:` note naming them so the developer can split the box per constraint 62. See `15_INTERACTIVES_BUILD_MODE.md`
79. **(Universal)** **A lesson page's `<h1>` carries that LESSON's own title — writer variation cannot change that.** On every lesson page (`-01`, `-02`, …), of every series and year level, the header is lesson-scoped: the `#module-code` `<h1>` holds the lesson **number** and the title `<h1><span>` holds the **lesson's own name**. The module code and module title belong to the overview page (`-00`). **Supersedes** the former universal "lesson `<h1>` = MODULE title, first `Lesson N` H2 demoted to a body `<h3>`" rule and **generalises constraint 69** (which scoped this to OSSC and was in fact describing the corpus norm). Corpus-verified: **1,105** lesson pages carry the lesson's own title vs **252** repeating the module title (the minority almost entirely pages with no writer-supplied lesson title, plus BLL phonics and single-file Fundamentals); the `#module-code` chip agrees **1,390 : 49**. **Fixed source order, applied identically however the writer structured the lesson:** (1) text inside the boundary tag, `[LESSON 2: Puanga]`; (2) text immediately after the boundary tag, `[LESSON 1] The night sky`; (3) the lesson's opening `[H2]` after `[Lesson content]`; (4) a `[Lesson Overview]`/lesson-menu heading naming the lesson; (5) fallback — the module English title **plus a visible `Designer/Developer To Do:` note** recording that no lesson title was supplied. A leading `Lesson N` / `Lesson N:` / `Lesson N -` prefix is **stripped** from whichever source wins; its presence is **never** a reason to demote the title into the body. **A lesson name the writer supplied twice** (boundary tag *and* opening `[H2]`) is **one** title, not a conflict — the header takes it and the duplicate body heading is dropped per constraint 47; a duplication must never trigger the module-title fallback. **One** title `<h1><span>` per lesson page at every level — the module-level Te Reo title is not repeated beside a lesson title (corpus 909 : 118); a second `<h1><span>` appears only where the writer gave *that lesson* its own bilingual name, and is then the **lesson's** English + Te Reo pair. The overview page is unchanged. See `01_PIPELINE_EXTRACTION_TAGS.md` → Template Title Patterns → Lesson Page Header
80. **(Universal — PageForge Compare Mode)** **PageForge Compare Mode (Mode 7)** is entered by the phrase `PAGEFORGE COMPARE MODE` (or `PAGEFORGE COMPARISON MODE` / `PAGEFORGE COMPARE`) **plus the uploaded PageForge-generated HTML**, and **only in the original conversion chat** — the writer's template and the developer's refined, go-live-quality HTML must be the genuine originals already in that chat; a run cannot be reconstructed from re-uploaded substitutes. Because `PAGEFORGE COMPARISON MODE` contains the substring `COMPARISON MODE`, **the leading word `PAGEFORGE` is the discriminator and is checked first** — it routes to Mode 7, never Mode 3. `UPDATE MODE` still outranks it; an uploaded `{CODE}_interactives.txt` inside this run is **evidence, not a Mode 6 work order**. **The measure is the writer's template, never the developer's taste:** PageForge's job is turning the writer's tags into the correct elements, so a difference that cannot be pointed back at a writer tag or the writer's own words — including any decision the developer took after liaising with the writer — is **never reported as a fault**; it is excluded, or held in the report's "For Gavin to judge — origin uncertain" section, never dropped without trace. **Build quality is judged only for interactives PageForge itself built, and only for non-complex types** (non-complex = a type PageForge already has a builder for: accordion, carousel/rotating banner, clickDrop, dragAndDrop, flipCard, glossary, hint, hintSlider, modal, selfCheck, shapeHover, speechBubble, tabs — a non-complex type left as a hand-off placeholder IS a finding; every other type is complex and its absence is by design). **BOUNDARIES are judged for EVERY interactive and every activity box** — complex or not, built, un-built or stitched — in both directions: content spilling **out** of a box that ended too early, and content **swallowed** into a box that ended too late. The two PageForge upload states (hand-off, carrying `cv2-int-ref` reference boxes with the raw content collapsed inside; and stitched, where the Page Stitcher removed both anchors) are detected **per interactive, never per file**, and a mixed upload is a normal, expected state. The mode **converts nothing, builds nothing and edits nothing** — not the writer's content, not the developer's HTML, not PageForge's HTML, not this project's knowledge files — and its single deliverable is one downloadable report written for Gavin. See `16_PAGEFORGE_COMPARE_MODE.md`
