75. **(Universal)** **A STANDALONE `[external link]` builds an `externalButton`; an INLINE one stays an anchor — position decides, not the tag.** Writers use `[external link]` and `[external link button]` interchangeably, so the tag alone is not a reliable signal. A link the writer gave **its own line/paragraph** (a call to action) renders `<a href="URL" target="_blank"><div class="externalButton">Text</div></a>`; a link sitting **inside prose, a list item, or a table cell** renders a plain `<a href="URL" target="_blank">Text</a>`. `[external link button]` **always** renders as a button regardless of position. The `external link` / `external link button` **tag distinction is retained** in the taxonomy — it is the *rendering* of a standalone `[external link]` that now matches the button form. **The test:** would removing the link leave a grammatically incomplete sentence? If yes → inline anchor. Containment in an `alert`, accordion, or speech bubble does not change the test — the prose relationship decides. Borderline → render the **anchor** and raise a `Red Flag:`. **THE DEFAULT LABEL:** a standalone external-link button whose writer text merely **names the destination** ("Gravity and Orbits"), or which carries **no label at all**, reads **"Go to website"** — the resource's own title is never used as button text. A writer-supplied **action** label ("Go to Stellarium website") is still honoured verbatim; the test is whether the words read as a call to action or as a title. This sits alongside — and does not overturn — constraint 55's "Go to dropbox" / "Go to portfolio" submission labels or constraint 65's "Go to quiz". See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Buttons and `01_PIPELINE_EXTRACTION_TAGS.md` → Tag Taxonomy → Link/Button Tags
76. **(Universal — Update Mode)** **Update Mode NEVER produces a finalized difference report for the designer.** No Update Mode run generates, writes out, presents, or offers a difference report of its actioned changes for Gavin — regardless of the intake channel (finalized report, direct-typed, project instruction), the classification (Routine or Major), or the scope. The run's own output **is** the record: the restated/normalised change list, the conflict report, the Repo Update Brief (with its drafted `12_CHANGE_LEDGER` row(s)), and the per-change log. Do not offer to produce one, and do not close a run by reminding anyone to email one. **The Persephone conflict catalog is unaffected** — a report-vs-report conflict is a different artefact on a different path (`11` → Section 7.1) and is still produced whenever one occurs. Standing designer instruction of 16 July 2026 (ledger `CL-0052`), superseding the report-to-Gavin limb of `CL-0006`; the rest of `CL-0006` (Persephone engaged only for report-vs-report conflicts) stands. See `11_UPDATE_MODE.md` → Sections 7, 15, 16
77. **(Universal)** **A `col-md-8` column is never nested directly inside another `col-md-8` column.** Where a row inside a `col-md-8 col-12` wrapper needs a column, use `col-md-12 col-12` (or a documented inner pattern such as the `col-md-6` pair) — never a `col-8`-family class. A `col-md-8` inside a `col-md-12`, and a `col-md-12` inside a `col-md-8`, are both fine. Applies to inner activity columns (`col-8`) too — and note that **an activity's inner column is specifically `col-12` (constraint 63)**, which satisfies this rule and is the value to use there rather than `col-md-12 col-12`. See `02_DATA_CONTENT_VERIFICATION.md` → Content Rules and `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Columns
78. **(Universal — Interactives Build Mode)** **Interactives Build Mode (Mode 6)** is entered by the phrase `INTERACTIVES MODE` **or** by the upload of a PageForge interactives worklist, which is self-identifying (header `INTERACTIVE REFERENCE — {CODE}` plus per-entry `REFERENCE CODE:` lines) — never to be confused with a content-source `.txt` (`--- CONTENT START ---` / `[TITLE BAR]` → Mode 1). It builds **only** the un-built interactives the worklist lists, as **anchored fragments** for PageForge's Page Stitcher: each build is wrapped in exactly `<section class="cv2-built" data-cv2-ref="{REFERENCE CODE}">`, the code copied **character-for-character**, **once**, never renumbered, re-ordered, abbreviated or nested. A worklist whose entries carry **no** reference codes is **not built** — the developer is asked to re-convert with the current HTML Generator. The fragment **starts at the widget's own wrapper**: the generated page already supplies the activity box, the row/column grid, the headings and the surrounding prose, so the mode never emits pages, menus, headers, footers, acknowledgements, activity boxes, `<html>/<head>/<body>`, or a `<script>` head include (the Stitcher injects the two `crossword`/`wordFind` includes itself). Output is complete downloadable file(s) — `{CODE}_interactives_built.html`, or batches of **up to 8** builds (`_1of3.html`, `_2of3.html`, …), every code in exactly one file. **ALL of the planned files are emitted in the SAME response**, back to back, after an announced plan: the ≤8 split is a file-size safeguard, never a pacing device, and the developer is never asked to prompt for the next file (no "say next"). Only a hard response-length limit may force a continuation, and it is then continued unprompted. *(Mode 5's deliberate one-file-per-response cadence — `CL-0011` — is a Split Mode rule and does **not** apply to this mode.)* The **component files remain the markup authority** (`03`/`04`/`05` COMP sections, `02` Section 06 for data patterns, `14` for family conventions) and **every hard constraint still applies** — including constraint 1 (writer content verbatim), 2 (no invented classes/CSS/JS), 3 (no visible tags), 4 (never guess a structure — closest documented pattern plus a visible note) and 5 (nothing buried in a comment). Where a worklist entry carries **two or more task interactives**, the fragment cannot split the page's activity box: build them all in `Content:` order inside the one section and add ONE visible `Designer/Developer To Do:` note naming them so the developer can split the box per constraint 62. See `15_INTERACTIVES_BUILD_MODE.md`
79. **(Universal)** **A lesson page's `<h1>` carries that LESSON's own title — writer variation cannot change that.** On every lesson page (`-01`, `-02`, …), of every series and year level, the header is lesson-scoped: the `#module-code` `<h1>` holds the lesson **number** and the title `<h1><span>` holds the **lesson's own name**. The module code and module title belong to the overview page (`-00`). **Supersedes** the former universal "lesson `<h1>` = MODULE title, first `Lesson N` H2 demoted to a body `<h3>`" rule and **generalises constraint 69** (which scoped this to OSSC and was in fact describing the corpus norm). **NOT A PRE-FLIGHT QUESTION.** This is settled universally, so it is never offered to the designer as a choice (there is no "module title or lesson title?" to ask), and the superseded wording it replaced is never surfaced as a live alternative. A designer answer that contradicts it is flagged back and confirmed, never followed silently — see `00B` → the pre-flight block. Corpus-verified: **1,105** lesson pages carry the lesson's own title vs **252** repeating the module title (the minority almost entirely pages with no writer-supplied lesson title, plus BLL phonics and single-file Fundamentals); the `#module-code` chip agrees **1,390 : 49**. **Fixed source order, applied identically however the writer structured the lesson:** (1) text inside the boundary tag, `[LESSON 2: Puanga]`; (2) text immediately after the boundary tag, `[LESSON 1] The night sky`; (3) the lesson's opening `[H2]` after `[Lesson content]`; (4) a `[Lesson Overview]`/lesson-menu heading naming the lesson; (5) fallback — the module English title **plus a visible `Designer/Developer To Do:` note** recording that no lesson title was supplied. A leading `Lesson N` / `Lesson N:` / `Lesson N -` prefix is **stripped** from whichever source wins; its presence is **never** a reason to demote the title into the body. **A lesson name the writer supplied twice** (boundary tag *and* opening `[H2]`) is **one** title, not a conflict — the header takes it and the duplicate body heading is dropped per constraint 47; a duplication must never trigger the module-title fallback. **One** title `<h1><span>` per lesson page at every level — the module-level Te Reo title is not repeated beside a lesson title (corpus 909 : 118); a second `<h1><span>` appears only where the writer gave *that lesson* its own bilingual name, and is then the **lesson's** English + Te Reo pair. The overview page is unchanged. See `01_PIPELINE_EXTRACTION_TAGS.md` → Template Title Patterns → Lesson Page Header
80. **(Universal — PageForge Compare Mode)** **PageForge Compare Mode (Mode 7)** is entered by the phrase `PAGEFORGE COMPARE MODE` (or `PAGEFORGE COMPARISON MODE` / `PAGEFORGE COMPARE`) **plus the uploaded PageForge-generated HTML — its ORIGINAL, un-stitched output, which is the only upload the mode asks for (constraint 81b)** — and **only in the original conversion chat** — the writer's template and the developer's refined, go-live-quality HTML must be the genuine originals already in that chat; a run cannot be reconstructed from re-uploaded substitutes. Because `PAGEFORGE COMPARISON MODE` contains the substring `COMPARISON MODE`, **the leading word `PAGEFORGE` is the discriminator and is checked first** — it routes to Mode 7, never Mode 3. `UPDATE MODE` still outranks it; an uploaded `{CODE}_interactives.txt` inside this run is **evidence, not a Mode 6 work order**. **The measure is the writer's template, never the developer's taste:** PageForge's job is turning the writer's tags into the correct elements, so a difference that cannot be pointed back at a writer tag or the writer's own words — including any decision the developer took after liaising with the writer — is **never reported as a fault**; it is excluded, or held in the report's "For Gavin to judge — origin uncertain" section, never dropped without trace. **Build quality is judged only for interactives PageForge itself built, and only for non-complex types** (non-complex = a type PageForge already has a builder for: accordion, carousel/rotating banner, clickDrop, dragAndDrop, flipCard, glossary, hint, hintSlider, modal, selfCheck, shapeHover, speechBubble, tabs — a non-complex type left as a hand-off placeholder IS a finding; every other type is complex and its absence is by design). **BOUNDARIES are judged for EVERY interactive and every activity box** — complex or not, built, un-built or stitched — in both directions: content spilling **out** of a box that ended too early, and content **swallowed** into a box that ended too late. The two PageForge upload states (hand-off, carrying `cv2-int-ref` reference boxes with the raw content collapsed inside; and stitched, where the Page Stitcher removed both anchors) are detected **per interactive, never per file**, and a mixed upload is a normal, expected state. The mode **converts nothing, builds nothing and edits nothing** — not the writer's content, not the developer's HTML, not PageForge's HTML, not this project's knowledge files — and its single deliverable is one downloadable report written for Gavin. See `16_PAGEFORGE_COMPARE_MODE.md`
81. **(Universal — PageForge Compare Mode)** **PageForge Compare Mode is entered ONLY by the typed trigger phrase, takes PageForge's ORIGINAL HTML as its only upload, and ignores every comment and developer note.** Three rules, all binding. **(a) NEVER ADVERTISE IT.** Only some developers are testing PageForge, so the mode is never mentioned, offered, suggested or asked about unless the developer types `PAGEFORGE COMPARE MODE` (or its accepted variants) themselves — most particularly not at the end of a `COMPARISON MODE` run, where the artefacts happen to be to hand: no "you can now run PageForge Compare" close, no asking whether they have PageForge files or are on the test programme, no naming the report for Gavin or the worklist as a next step. Nothing else starts it either — not PageForge-looking files, not a `cv2-int-ref` box spotted in an upload, not a worklist arriving on its own. The sole exception is a developer who raises PageForge first. The `PAGEFORGE`-prefix discriminator in `09A` exists so the mode is not entered **by accident**; it is not a licence to raise it. **(b) THE ONLY UPLOAD IS PAGEFORGE'S ORIGINAL HTML — NEVER ASK FOR THE WORKLIST.** The tester uploads the PageForge-generated pages **exactly as the generator produced them**, and nothing else; `{CODE}_interactives.txt` is **not an input to this mode** and is never requested. It is not needed, because the two artefacts the mode already has carry everything it used to supply: the **writer's template** is in the chat from the original conversion turn, and **PageForge's own pages** record its decisions directly — a `cv2-int-ref` reference box IS PageForge stating it did not build that interactive; the box's collapsed `cv2-int-raw` block IS the writer content PageForge captured into it (what the worklist's `Content:` line carried); and the activity wrapper the box sits inside IS PageForge's ownership decision (what the worklist's `Activity:` line carried). On an un-stitched page, finished widget markup is therefore PageForge's own build by definition — there is no third possibility. **The one requirement that replaces the worklist: the pages must be the ORIGINAL, un-stitched output.** That evidence lives in the `cv2-*` markup, which PageForge's Page Stitcher removes, so a module already taken through Mode 6 and stitched no longer shows what PageForge did. Detect a stitched upload, say so plainly, and ask for the untouched originals; if they genuinely no longer exist, run with the documented limits (interactives present as finished markup are marked `state unknown`, carry no class C finding and cannot have their boundary verified) and state those limits in the report header and the chat. A worklist a tester volunteers anyway is accepted as **corroborating evidence, never a Mode 6 work order**, and its absence is normal and never remarked on. **Supersedes the `CL-0072` limb that made the worklist a required input** (designer decision, 13 August 2026, `CL-0081`). **(c) COMMENTS AND DEVELOPER NOTES ARE IGNORED ENTIRELY**, exactly as in Mode 3 (`09B` Exclusion 1) — in both files, in both directions, added, reworded, restyled, relabelled, moved or deleted: PageForge's own red notes (`Writers Note:`, `Red Flag:`, `Designer/Developer To Do:`, `Note from {author}:`), notes the developer added (including ones addressed to the course writer), restated writer instructions, and HTML comments. They are developer scaffolding that changes continually as writer and developer exchange information during a build, never module content, and never evidence of how PageForge read the writer's template. The one thing NOT excluded is a writer `[tag]` or the writer's own content **leaking onto the page as visible text** — that is content gone wrong (class A, and D where content was lost). See `16_PAGEFORGE_COMPARE_MODE.md`

82. **(Universal)** **The document shell is emitted in full on EVERY generated page — the opening `<body class="…">` tag above all.** A whole-page build (Mode 1 conversion, Mode 2 MTK conversion, Mode 5's **base** file) always emits, in order and all present: `<!doctype html>` · `<html template="…">` · `<head>` … `</head>` · **`<body class="…">`** · `<div id="header">` · `<div id="body">` · `<div id="footer">` · `</body>` · `</html>`. **The opening `<body>` tag is not optional, is never implied by the `#header` div that follows it, and is never omitted because the structural reference omits it.** The defect this closes is a page whose `</head>` is followed straight by `<div id="header">` — the browser then opens an implicit body with **no class**, every `container-fluid` / `fundamentals` / `inquiry` / `reoTranslate` rule that hangs off that class fails silently, and the page renders wrongly while looking plausible in source. **The class value is derived, never guessed** — Standard `container-fluid`; Bilingual `container-fluid reoTranslate` (plus `language`/`translation` attributes); Fundamentals `fundamentals container-fluid`; Inquiry `inquiry container-fluid`; Combo `container-fluid` — per `06_TEMPLATE_RECOGNITION.md` → Quick Identifier Table and Document Shell. **In Mode B this is one of the defects that is fixed silently rather than inherited:** MXFU401 and XTAS101 are the known reference modules missing the tag, and a reference module missing `<body>` is corrected in the output, never copied (`06` §4.2). If a page's sub-type genuinely cannot be resolved, emit the Standard `container-fluid` default **plus** a visible `Designer/Developer To Do:` note — never a class-less `<body>`, and never no `<body>` at all. **Carve-outs — these deliberately emit no `<body>` and are not in scope:** Interactives Build Mode fragments (constraint 78 — the section starts at the widget's own wrapper), and Split Mode **section** files (`13_SPLIT_MODE.md` — only the base file carries the shell). Verified by the `02_DATA_CONTENT_VERIFICATION.md` Template & Structure checklist. See `06_TEMPLATE_RECOGNITION.md` → Document Shell / §4.2
