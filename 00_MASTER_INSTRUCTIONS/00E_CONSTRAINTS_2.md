58. **Split Mode (Mode 5)** is triggered by the precedence phrase `SPLIT MODE`. It is a **packaging variant of Conversion** for a **single-page** module whose full output is too long to emit in one pass: it runs the entire Conversion Pipeline unchanged and only changes how the finished page is packaged — emitting one `<CODE>-base.html` (the complete single-page scaffold, whose `#body` holds **only** an ordered list of `<!-- PAGEFORGE-SPLICE id="X" -->` markers, one per lesson in order, with header/menu/footer/acknowledgements fully built and **no `stickyNav`**) plus one `<CODE>-lesson-<id>.html` per slot (the raw `#body` content for exactly that lesson, wrapped in `<!-- PAGEFORGE-SECTION id="X" -->` … `<!-- /PAGEFORGE-SECTION -->`, including that lesson's own `<!-- N -->` delimiter as the first line). **These files are emitted one per response: the first response returns the base file only, and each subsequent designer prompt returns the next single section file, in order — never more than one file in a single turn.** Both the base and every section file additionally carry highly detailed **`PAGEFORGE-GUIDE-START` … `PAGEFORGE-GUIDE-END`** comment blocks giving a human developer exact manual-stitch instructions — in the base, a guide block at each splice point naming which section file fills it and in what order; in each section file, a guide block (placed **outside** the section's content markers so a manual copy of the content doesn't drag the guidance along) naming the base splice point this section fills. Ids are `intro` then zero-padded `01`, `02`, … (case-insensitive, unique); ids line up **one-to-one** between base and sections (no orphans, no duplicates, at least one slot). PageForge's Page Stitcher recombines these into one `<CODE>.html` whose `#body` is **byte-identical** to a one-pass single-page build, with **no `PAGEFORGE-*` markers surviving** — the Stitcher strips both the `PAGEFORGE-SPLICE`/`PAGEFORGE-SECTION` markers and every `PAGEFORGE-GUIDE` block. A lesson whose content cannot be produced is emitted as its section file with a **visible red flag** inside it — **never an omitted slot** (an omitted slot fails the stitch). Split Mode applies to **single-page modules only**; a genuinely multi-page module (`[LESSON]` / `[End page]`) uses the **Page Boundary System** and is **never** split — the two systems are distinct. When a module is identified as single-page, proactively **offer** Split Mode (more prominently when the output is large); it runs only when the user explicitly invokes it. See `13_SPLIT_MODE.md`
59. **(Universal)** A **fourth source-specific red-note prefix, `Designer/Developer To Do:`**, joins the red-note family (`Note from {author}:` / `Writers Note:` / `Red Flag:`). It marks a **deferred piece of a known, correctly-built pattern** — an asset, URL, or setup the developer must supply during production (e.g. an Audiovisual item to be added, an image to create and embed, a `stickyNav.js` file to set up, a placeholder persona/character/overview to confirm, a curriculum statement to add as a later revision request). The pattern **is** built; only the pending piece is flagged. Rendered in the standard **red + bold** form (`<p style="color: red; font-weight: bold;">Designer/Developer To Do: ...</p>`), always **visible**, never a hidden comment. It is **distinct from `Red Flag:`**: `Red Flag:` signals a genuine defect/ambiguity/unbuildable structure; `Designer/Developer To Do:` signals something right-but-pending. Most often raised by a subject **global-parameter** convention (constraint 60). **Extends the existing red-note scheme** (this is the sole permitted designer-message inline style — constraint 2). See `02_DATA_CONTENT_VERIFICATION.md` → Source-Specific Red-Note Prefixes and `01_PIPELINE_EXTRACTION_TAGS.md` → Red Text Handling
60. **(Cohort/series-scoped)** **Subject global parameters live in `14_SUBJECT_GLOBAL_PARAMETERS.md`.** When converting or advising on a module that belongs to a documented subject cohort/series (Languages Phase 1–4, Pathways, Taonga, CED Phase 5, FUNdamentals H&PE, LS, BLL, BLLR, MiW/WJ, HPE content lessons, Technology), consult `14` for that subject's standing look-and-feel and structural conventions and apply them **within their stated scope**. These conventions **override generic patterns within their scope**, but **Mode B sibling authority still wins** on structure (a built same-series predecessor beats this file where they conflict — raise a `Red Flag:`). `14` introduces **no new CSS/JS or invented classes** — every class/code block it records was supplied by the design team (constraint 2). See `14_SUBJECT_GLOBAL_PARAMETERS.md`
61. **(Universal)** For an iStock URL, the **iStock ID is the number immediately following `gm` in the URL slug** — it always equals the asset page's **"Stock photo ID"** field (and the preview-image watermark ID). **Dual-ID URLs** (the current iStock format) carry two hyphen-separated numbers after `gm` — `gm{A}-{B}` (e.g. `gm2194652495-612793002`): the ID is **`A`**, the first number (→ `iStock-2194652495.jpg`); the trailing number `B` is a secondary/legacy catalogue identifier and is **NEVER** used — not for filenames, not for acknowledgements citations, not for iStock-acks-file matching. **Single-ID URLs** (the legacy format, e.g. `gm957693546`) are unchanged. **Position decides, never digit count, recency, or proximity to the query string** (extraction aid: `gm(\d+)(?:-\d+)?` — capture group 1 is the ID). The `images/iStock-{ID}.jpg` filename, the acks citation, and the acks-file match must all carry the **same** ID for a given asset. See `01_PIPELINE_EXTRACTION_TAGS.md` → Images (Mode D / Mode P filename construction; iStock Acknowledgements File) and `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Acknowledgements (Entry format)
62. **(Universal)** **Each `activity` wrapper contains at most ONE interactive component.** When the writer places two or more interactives under a single activity heading, **split them into separate sequential activities** — the first interactive keeps the writer's activity number; each subsequent interactive becomes the next activity letter — and **renumber the following activities accordingly** (e.g. a trailing 1E Word Find becomes 1F). Flag the split with a visible red note (`Red Flag:` prefix) so the renumbering is auditable against the writer's source. Supporting elements inside the activity (audio buttons/triggers, images, hover translations, instructional text and lists) are NOT counted as interactives — the count applies to the whitelisted interactive components that form the activity's task. See `03_COMP_CORE_INTERACTIVES.md` → COMP_00 (Universal Rules) and `02_DATA_CONTENT_VERIFICATION.md` → Verification Checklist
63. **(Universal)** **An activity's inner text column is `col-12`; text and interactive share ONE inner row at the default wrapper width, and split into two rows only when the wrapper is widened.** The inner column that carries an activity's plain text content (headings, instructions, paragraphs, lists) is **`col-12`** — **never** `col-md-8 col-12`. The wrapper itself already sets the reading width, so an inner `col-md-8` narrowed the prose a second time. Then, **the split is conditional on the wrapper's width**: **(a) DEFAULT wrapper (`col-md-8 col-12`)** — the heading, instructions and the interactive all sit together in **ONE** inner `row` > `col-12`; there is no split, because there is no width difference to express. **(b) WIDENED wrapper (`col-12` Standard / `col-md-11 col-12` Inquiry & Fundamentals / `col-md-12 col-12` full width — constraint 56)** — the two-row split is retained: the text sits in its own inner `row` > `col-12` and the interactive follows in a **separate** inner `row` at the wrapper's own width. A **text-only** activity (no interactive) needs no split at either width — its single `row` > `col-12` carries the heading and prose. **Supersedes the former "text and interactive ALWAYS sit in separate inner rows; the text stays at `col-md-8`" rule** (`CL-0036` → `CL-0048`), which double-narrowed the prose and split rows that had nothing to separate. Constraint 56 (wrapper widths) is unaffected — this changes only what happens *inside* the wrapper. See `02_DATA_CONTENT_VERIFICATION.md` → Interactive Wrapper Width and `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Activities / Columns
64. **(Universal)** **All Creative Services videos are Vimeo links.** A video produced by Creative Services (a Te Kura in-house / Audiovisual production) is embedded as the designer-supplied **Vimeo `videoSection` scaffold** with the video ID left pending (`src="https://player.vimeo.com/video/"` — never guess an ID), immediately preceded by a visible red+bold note `Designer/Developer To Do: add vimeo embed for [audiovisual item x]` identifying the item. The scaffold is emitted exactly as supplied — including its trailing `<!-- &amp;start=0 --> <!-- &amp;end=0 -->` time-parameter placeholders, a narrow permitted comment exception (constraint 37). External YouTube videos are unchanged; where the producer is unclear, raise a visible `Red Flag:`. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Video Embed → Creative Services Videos (Vimeo)
65. **(Universal)** **`[MTKquiz]` builds a numbered activity box holding up to four things — and NEVER the quiz's own content.** When the writer's template carries the `[MTKquiz]` tag (any modifier combination — `[engage]`, `[type the answer]`, `[Teacher marked …]`, etc.), emit an `activity` wrapper carrying the **next consecutive activity number — even where the writer assigned none** — containing, in this order and with nothing else: **(1)** the **quiz title** as the first child, an `<h3>` reading **`Quiz`** by default or the writer's own quiz title verbatim where supplied; **(2)** any **quiz instructions** the writer wrote for students, as normal paragraph text — **omitted entirely where the writer supplied none, leaving a valid three-child box**; **(3)** a visible red+bold `Designer/Developer To Do:` note instructing the designer to create the quiz in **MTK DEV** and **orgunit link** it to this module; **(4)** `<a href="#" target="_blank"><div class="button">Go to quiz</div></a>` (blank href — the developer wires in the D2L quiz quicklink URL) — never a dropbox button. **The quiz's questions, options and answers are NEVER generated into the HTML** in any form — visible, listed, or commented — and the omission is **silent** (no `Red Flag:`); the material stays in the Writers Template, from which the designer builds the quiz. This is the second documented removal under constraint 1, and it **reverses** CL-0038's "writer-supplied quiz content stays visible" limb (CL-0082, 21 August 2026). The `dropbox` wrapper modifier of constraint 43 does not attach. `MTK` here means the My Te Kura D2L quiz tool (MTK DEV its authoring environment), not the `07` MTK Writers Template pathway. **WJ series:** when `[MTKquiz]` co-occurs with an in-page quiz tag (e.g. `[Multichoice quiz]`), `[MTKquiz]` takes precedence and the in-page component is not built. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Buttons → MTK Quiz
66. **(Universal)** **Acknowledgement entry titles are the official published title, verbatim — including a trailing ". stock photo".** A stock-asset acks title is cited exactly as it appears on the platform: sentence casing, internal punctuation, and any trailing **". stock photo"** suffix retained when it is part of the official iStock title (e.g. *"Tourist visiting lake Wanaka, New Zealand. stock photo"*, iStock 1137701281). Never strip, re-case, or title-case the published title; a URL-slug derivation is only an approximation and yields to the official title (iStock acknowledgements file per constraint 53, or the asset page) wherever available. The **alt-text prohibition on "stock photo" is unchanged** (constraint 52) — alt text is a brief description for screen readers and drops platform-title suffixes; the acknowledgements cite the title as published. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Acknowledgements (Entry format / Sourcing)
67. **(Universal)** **The overview (`-00`) module menu is built from the canonical tab set — never mirrored from the reference.** The tabbed `-00` menu uses the fixed canonical set **Overview → Knowledge → Practices → Information → Standards/Assessment** (shell from the canonical template `refresh_NCEA_overview 3.html`; `tooltip="Overview"` on `#module-menu-button`), including **only** the tabs the Writers Template supplies content for (omission rule: absent content → remove BOTH the `<li>` and its `.tab-pane`; never synthesise placeholder content) — the reference module's particular tab selection is never the template. Writer sections are matched by **meaning** and labelled by **canon** (tab labels, "Learning Intentions" / "How will I know I have learned it?", "We are learning:" / "I can:", "Assessment for Learning"); exactly ONE variation is emitted per variable panel (Overview Var 1 side-by-side / Var 2 stacked; Standards Var A ≤3 / Var B >3 standards); headings follow the canonical table (`<h4><span>` Overview/Knowledge/Practices titles; `<h5>` no-span labels and all Information/Standards headings — superseding the former all-`<h4>`/never-`<h5>` overview-menu rule); long panels take `overflowYScroll` `scroll="500"`; `Designer note:` lines are stripped. Applies to the **tabbed** overview archetype — a series whose overview menu is legitimately simplified/absent (per `10` §2/§4) keeps that archetype; lesson-page simplified menus are unchanged (constraint 23). See `01_PIPELINE_EXTRACTION_TAGS.md` → Module Menu Structures → Module Overview Pages (`-00`) — Canonical Tabbed Menu
68. **(Universal)** **Supervisor buttons are built with the `super-content-button` family; the `supervisorContainer` trio is retired.** Triggers: `[supervisor note]` / `[supervisor button]` / `[supervisor]`, or a red-text `Supervisor:` / `Supervisor's Notes:` prose lead-in (a supervisor trigger, not a `Writers Note:`). Activity-bound notes → **Shape A** (`super-content-button` + `number` on the `.activity`; reveal panel is the activity's FIRST child); standalone section notes → **Shape B** (`super-content-button` on the `.col`); a section note beside content → **Shape C** (`paddingL` button col + `paddingR` content col). In all three shapes the **outermost row is `<div class="row supervisor">`** — the only exception is a note nested inside another widget (accordion/clickDrop/inquiryPanel), which keeps the widget's own row. The reveal panel keeps its invariant 4-level nesting (`super-content row` → `row` → `col-12` `<h3>` + `col-12` content; default heading "Supervisor note"; note text verbatim); default content column `col-md-8 col-12`; existing activity modifiers are kept and `super-content-button` appended. The legacy `supervisorContainer`/`supervisorButton`/`supervisorContent` trio and the minority `activity supervisor` form are **recognise-only — never emit**. `[side alert]` affects placement only. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Supervisor Button
69. **(SUPERSEDED by constraint 79 — GENERALISED from OSSC to universal, 3rd August 2026, ledger `CL-0069`. Retained for history; the rule below is now simply what every series does, so there is no longer an OSSC exception to apply.)** **On an OSSC lesson page the `<h1>` carries the LESSON title, not the module title.** *For the OSSC (Online Safety — Scams) series at **every** year level*, a lesson page (`-01`, `-02`, …) carries a **single** `<h1><span>` holding that page's own lesson title (taken from the lesson's opening H2, minus any `Lesson N` / `Lesson N:` prefix), and that title is **NOT** repeated as a body `<h3>`. This **overrides** the universal "lesson `<h1>` = module title" rule (constraint 23 family) **and** the Years 9–10/NCEA dual-title rule for OSSC lesson pages — an OSSC lesson page carries **one** `<h1><span>`, never the English + Te Reo pair, at any level. The `#module-code` `<h1>` (zero-padded lesson number) is unchanged, and the OSSC **overview** page (`-00`) is unchanged — it keeps the module title, dual where its level requires. All other series follow the universal rule. See `01_PIPELINE_EXTRACTION_TAGS.md` → Template Title Patterns → Lesson Page Header
70. **(Series-scoped — OSSC)** **An OSSC lesson module menu may open with a `[Lesson Overview]` lead-in paragraph.** *For the OSSC series at **every** year level*, where the writer's `[Lesson Overview]` supplies a descriptive sentence (typically "Ākonga will…") ahead of the learning/success labels, it is rendered as a `<p>` **above the first `<h5>`**, inside the same `col-md-8 col-12`. The paragraph is **writer content** (constraint 1, verbatim) — not label text, and not subject to the label normalisation of constraint 24. This is **compatible with**, not a reversal of, the standing ban on `<p>` elements *between a heading and its list* (constraint 23): the lead-in sits above the first heading, and no `<p>` ever separates an `<h5>` from its `<ul>`. Where a lesson supplies no such sentence, no lead-in is emitted — its absence is not an error. All other series: no lead-in. See `01_PIPELINE_EXTRACTION_TAGS.md` → Module Menu Structures → Lesson Pages — Simplified Module Menu
71. **(Universal)** **Footer navigation `href`s are left EMPTY.** Every footer navigation anchor ships with `href=""` — `prev-lesson`, `next-lesson`, and `home-nav` alike. The conversion **never** computes sibling filenames (`MODULE_CODE-XX.html`) into them; the links are wired up at publish time in D2L. The per-position `<li>` composition rule is **unaffected** (overview → `next-lesson` + `home-nav`; middle → all three; final → `prev-lesson` + `home-nav`), as are the `id`/`class` and `target` attributes, on which the publish-time wiring depends. **Mode B:** there is nothing to re-point — if a reference file carries populated hrefs, do NOT copy them and do NOT rewrite them to the new module code; **empty them**. This supersedes the former "replace ALL navigation hrefs to use the NEW module code" instruction. See `01_PIPELINE_EXTRACTION_TAGS.md` → Footer and Acknowledgements
72. **(Universal)** **A REQUESTED AI asset triggers `acksAI`, even though it does not exist at conversion time.** The `acksAI` modifier (constraint 53 family; `<div class="acks acksTemplate acksAI">`) is applied on the basis of what the **finished module will contain**, not what exists when the conversion runs: where the writer has **requested** an AI-generated asset (typically a red-text CS instruction such as *"CS: could you create an image for this please?"*), apply `acksAI` **in anticipation** and pair it with a visible `Designer/Developer To Do:` note recording that the asset and its acknowledgement entry are still to be created. A request for a **non-AI** asset (a photo to source, a hand-drawn diagram, an Audiovisual video) does **not** trigger the modifier — it gets its own `Designer/Developer To Do:` note without it. Where the production method is unclear, **apply `acksAI` and say so in the note** (trivially removable by the designer; a missing `acksAI` on a shipped AI asset is a compliance miss). See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Acknowledgements → Basic block
73. **(Universal)** **The acknowledgements page-label annotation reads `Lesson N.N`, never `Page N.N`.** Each **media-carrying** `acksLesson` div inside the acknowledgements block opens with a comment naming the page whose media it covers — `<!-- Lesson 0.0 -->`, `<!-- Lesson 1.0 -->`, `<!-- Lesson 2.0 -->`, … — matching the `acksLesson` class name and the team's own way of referring to the pages. This annotation is a **permitted comment exception** (constraint 37): it is a structural grouping label pairing a machine-ordered run of identical divs with the page each belongs to, and carries **no** student content, designer-action note, ambiguity, or interactive answer — anything of that kind is still a visible red note. The three standard boilerplate divs (opening apology, "All other images ©…", closing Te Kura copyright) carry **no** label. See `05_COMP_LANGUAGE_MEDIA_LAYOUT.md` → Acknowledgements → Accordion structure and `02_DATA_CONTENT_VERIFICATION.md` → Comment & Red Flag Policy
74. **(Universal)** **No emoji in modules — strip them, list them, and disclose the removal.** Finished modules carry **no emoji**: where writer content contains them, the Convertor **removes** them. This is the **sole documented exception to constraint 1's prohibition on modifying writer content** — the only case permitting *deletion* rather than re-casing. **Exempt — kept verbatim: ticks and crosses** (`✅ ✓ ✔ ☑ ✗ ✘ ❌ ❎`), which carry meaning (correct/incorrect, done/not done) rather than decoration; every other emoji is stripped. Rules: a **leading** emoji is removed along with its separating whitespace; a **run of two or more** consecutive emoji-prefixed lines becomes a single `<ul>` with one `<li>` per line (a lone emoji-prefixed line stays a `<p>`); an emoji **inside prose** is removed and the surrounding spacing normalised to a single space; **wording is never otherwise altered** (typos and all). The removal is **disclosed, never silent** — one visible note per affected page, at the first removal on that page: `<p style="color: red; font-weight: bold;">Red Flag: Emoji have been removed from this content per the no-emoji rule. Ticks and crosses are retained.</p>` (prefix is `Red Flag:` — a Convertor-made change to writer content). A genuinely borderline glyph is **kept** and red-flagged, never stripped on a guess. Self-reflection emoji **images** (`self-reflection-emoji/*.png`) are images, not characters, and are unaffected. See `01_PIPELINE_EXTRACTION_TAGS.md` → Special Characters → No Emoji in Modules
