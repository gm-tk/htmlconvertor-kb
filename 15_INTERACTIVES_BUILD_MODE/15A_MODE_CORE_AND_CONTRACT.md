# 15 — Interactives Build Mode (Mode 6)

> **PURPOSE.** PageForge's **HTML Generator** (the V2 converter) builds a module's pages
> automatically, but leaves the interactives it cannot yet build as **reference-code
> placeholders** and lists them in a companion worklist, `{CODE}_interactives.txt`. In this mode
> the Convertor takes that worklist and returns **production-quality HTML for every un-built
> interactive**, each wrapped in its reference-code anchor, so PageForge's **Page Stitcher**
> can drop each build into the exact spot in the module pages automatically.
>
> This is a **narrow, additive mode**: it builds interactive **fragments** for pages that already
> exist. It never converts a module, never rebuilds pages, menus, headers, footers,
> acknowledgements or activity boxes, and it changes **nothing** about Modes 1–5.

---

## 1. TRIGGER & AUTO-DETECTION

The mode runs when **either** of these is true:

1. **The phrase `INTERACTIVES MODE` appears in the message** (explicit invocation), **or**
2. **an uploaded/pasted `.txt` is a PageForge interactives worklist** — recognised by its header
   block:

```
=====================================
INTERACTIVE REFERENCE — {CODE}
Generated by HTML Generator V2 …
=====================================
```

   together with per-entry `REFERENCE CODE:` lines. A worklist is **self-identifying**, so the
   developer does not have to type anything — dropping the `.txt` in is enough.

**Never confuse the worklist with a content source.** The two `.txt` files are unrelated:

| File | Opens with | Meaning |
|---|---|---|
| **Content source** `.txt` (Mode 1) | `--- CONTENT START ---` then the first `[TITLE BAR]` | Convert the whole module → `00A`/`00B` Conversion Pipeline |
| **Interactives worklist** `.txt` (this mode) | `INTERACTIVE REFERENCE — {CODE}` + `REFERENCE CODE:` lines | Build only the listed interactives → this file |

If a message carries **both**, ask which the developer wants first — never silently do both.

**Precedence.** `COMPARISON MODE` and `UPDATE MODE` still take precedence over everything (a
worklist uploaded inside a Comparison or Update run is not built; say so and ask). Otherwise a
worklist upload is unambiguous and outranks the ordinary Conversion/Advisory signals.

## 2. WHERE THIS MODE SITS IN THE PIPELINE (why the anchors matter)

1. A developer converts a Writers Template + Media List in PageForge's **HTML Generator**. The
   interactive hand-off is the generator's **default** — there is no toggle to tick. It produces
   (a) the module's HTML pages, in which every un-built interactive is a **reference-code box**
   carrying a unique code (with the raw captured content collapsed inside it, expandable via the
   box's arrow), and (b) the `{CODE}_interactives.txt` worklist, in which every entry is headed
   by the **same** code.
2. The developer uploads the `.txt` **here**. This mode builds the interactives.
3. The developer uploads the built file(s) **plus** the module's HTML pages to PageForge's
   **Page Stitcher**, which finds each code, replaces the page marker with the matching build,
   and removes both anchors.

If the output loses, alters or duplicates a single reference code, the stitcher cannot place that
build. **The anchors are the contract.**

## 3. FIRST ACTION on every uploaded worklist

1. Confirm the header (`INTERACTIVE REFERENCE — {CODE}`) and read
   `STILL UN-BUILT (placeholders to develop): N` — that number is the workload and drives the
   file-split plan (§6).
2. Confirm the entries carry `REFERENCE CODE:` lines (format `{CODE}-INT-{NN}-{SS}-{type}`).
   **If they do not**, the module was converted by an **old** generator build (or with the
   reverting `INTCOLLAPSE_OFF` toggle set) — stop and tell the developer to re-convert with the
   current HTML Generator (the codes are its default output) and upload the new `.txt`. **Never
   build from a worklist without reference codes** — an unanchored build cannot be stitched.
3. Post the **build plan** (§6) before generating anything.

## 4. THE ANCHOR CONTRACT — the golden rule

Every built interactive is wrapped **exactly** like this, using the entry's REFERENCE CODE
character-for-character:

```html
<section class="cv2-built" data-cv2-ref="XDLS908-INT-01-01-dragAndDrop">
    …the finished interactive HTML…
</section>
```

- `class="cv2-built"` — exactly this class token; nothing may be added to it.
- `data-cv2-ref` — the entry's REFERENCE CODE, **character-for-character**. (The stitcher also
  tolerates the bare form `XDLS908-01-01`, but the full code is the standard — always use it.)
- The section's **inner** HTML replaces the page marker wholesale; the `<section>` tag itself is
  discarded. So the FIRST element inside the section is what lands in the page — normally the
  widget's own wrapper div.
- **One `<section class="cv2-built">` per worklist entry**, even when the entry's `Type:` line
  lists several components (`clickDrop + speechBubble + carousel`) — see §9.
- Never invent, renumber, re-order, abbreviate or "correct" a code. Never emit the same code
  twice. Never nest one `cv2-built` section inside another.
- The `File:` and `Placeholder marker:` lines are **context only** — the code is the anchor.
- No `>` character inside any attribute value anywhere in the output.

## 5. WHAT THE PAGE STITCHER DOES WITH IT (so you know what breaks if the contract slips)

1. Auto-detects an "interactive insertion" upload (the built file(s) + the module pages).
2. Indexes the sections by reference code. A **duplicated** code is a hard error — nothing
   downloads.
3. Replaces each page marker `<div class="cv2-int-ref" data-cv2-ref="…">CODE…</div>` with the
   matching section's inner HTML. Both anchors disappear from the finished pages.
4. A code that was **not** built stays on the page as its loud reference box and is reported as a
   warning — the developer can stitch again later with the missing file. A code that was built
   but matches **no** marker is reported as unused (usually a typo in the code — **this is the
   failure to fear most**).
5. Injects the `js/crossword.js` / `js/wordFind.js` head includes automatically when it places a
   crossword or wordFind build (§15B).
6. Downloads the finished pages (a zip when the module has more than one page).

## 6. OUTPUT FILES + THE SPLITTING SAFEGUARD

Deliver complete, downloadable HTML file(s) — never loose snippets in chat.

| Un-built count N | Files |
|---|---|
| 1–8 | ONE file — `{CODE}_interactives_built.html` |
| 9+ | `ceil(N/8)` files of up to 8 builds each, in worklist order — `{CODE}_interactives_built_1of3.html`, `_2of3.html`, `_3of3.html` … |

Plus the judgement rule: if the **current** file is getting long (several large data-table builds
may fill a file at 3–4 entries), close it early after the last complete `</section>`, say which
codes moved to the next file, and carry on there. **Never truncate an interactive across files**;
never leave a section unclosed; **every code lands in exactly one file, exactly once**.

Announce the plan first (one line per file listing its codes), then generate **ONE file per
response**, ending with "Say **next** for file X of Y." The stitcher accepts any number of built
files in one upload, so splitting costs the developer nothing.

```
Build plan — 19 interactives across 3 files:
  1of3: XDLS908-INT-01-01-dragAndDrop … XDLS908-INT-02-03-carousel   (8 builds)
  2of3: XDLS908-INT-03-01-accordion  … XDLS908-INT-05-02-flipCard    (8 builds)
  3of3: XDLS908-INT-06-01-tabs       … XDLS908-INT-08-01-selfCheck   (3 builds)
Generating file 1 of 3 now — say "next" for file 2.
```

File skeleton (the stitcher reads only the `cv2-built` sections; the rest is for humans):

```html
<!DOCTYPE html>
<html lang="en">
<head><meta charset="utf-8"><title>{CODE} — built interactives (file 1 of 2)</title></head>
<body>
<!-- PageForge built-interactives file. Upload together with the module's HTML pages
     to the Page Stitcher — each build is placed at its reference code automatically. -->

<section class="cv2-built" data-cv2-ref="…">
    …
</section>

</body>
</html>
```

## 7. QUALITY CHECK before emitting each file

1. Every planned REFERENCE CODE present **exactly once**, character-identical to the `.txt`.
2. Every `<section class="cv2-built">` closed; tags balanced inside; no section nested in another.
3. No `🔴`, `[RED TEXT]`, `[square-bracket tags]`, ASCII table borders or other worklist
   artefacts anywhere in the output.
4. Answer keys and pairings complete and consistent (every drag has a drop, every quiz has a
   correct answer, counts match), and the buttons row uses the component's **own** classes per
   the component file's button table (`mcqReset`/`mcqAswers` vs `mcqAnswers`, `memGameReset`,
   `cloReset` …) — copy, never recall — respecting the **autoCheck ⇒ Reset-only** rule.
5. All writer text present, or covered by a visible `Designer/Developer To Do:` note — nothing
   silently lost (constraint 1).
6. File named per §6 and self-contained.

## 8. WHICH KNOWLEDGE TO LOAD — and the authority order

This mode reuses the project's **existing** component knowledge; it does not carry a second copy
of it.

1. **The component files are the markup authority** — `03_COMP_CORE_INTERACTIVES.md` (COMP_00
   universal rules + the specific COMP section), `04_COMP_SEGMENTS_OVERLAYS.md`,
   `05_COMP_LANGUAGE_MEDIA_LAYOUT.md`. Load COMP_00 plus the section(s) for the types on the
   entry's `Type:` line. These files carry every designer-confirmed ruling in the change ledger,
   which is why they outrank any older summary.
2. **`02_DATA_CONTENT_VERIFICATION.md` → Section 06 (Interactive Data Patterns)** — for reading
   a captured data table and for an `unclassified` entry, where the widget must be inferred from
   the data shape.
3. **`15B` (this topic)** — the worklist format and the fragment-specific build rules; **`15C`**
   — a worked entry end to end.
4. **`14_SUBJECT_GLOBAL_PARAMETERS.md`** — when the module code belongs to a documented family
   (BLL, WJ/WJFUN, HPE, LS …), its scoped conventions still apply to the interactive.
5. The finished module library is corroborating evidence, **not** an authority — older modules
   carry superseded variants.

All the project's **ABSOLUTE RULES and hard constraints still apply in this mode**: never invent
classes, structures, CSS or JavaScript; never reword writer content; never render square-bracket
tags as visible text; never bury anything in an HTML comment; never disclose an interactive's
answers in a comment. Where a build cannot be expressed with a documented pattern, emit the
closest documented pattern **plus** one visible note — never a guess (constraint 4).

## 9. MULTI-COMPONENT ENTRIES AND THE ACTIVITY-BOX CARVE-OUT

An entry whose `Type:` line lists several components (joined with ` + `) means the captured
region holds several components: **build them ALL, in the order the `Content:` block shows,
inside that one section** — the reference code carries only the first type, and one marker on the
page can only be replaced once.

This is a **mode-scoped consequence, not an override of constraint 62** ("each `activity`
wrapper contains at most ONE interactive component"). The activity box already exists in the
generated page and a fragment cannot split it. So where an entry carries **two or more task
interactives**, build them in order and open the section with **one** visible note naming them:

```html
<p style="color: red; font-weight: bold;">Designer/Developer To Do: this activity box holds 2 interactive components (clickDrop, selfCheck) — split it into sequential activities per constraint 62 when finalising the page.</p>
```

Supporting elements (audio buttons/triggers, images, hover translations, instructional text and
lists) are **not** counted as interactives — no note is needed for those.

## 10. TONE + INTERACTION

Reply briefly and practically. Lead with the plan, deliver the file(s), and finish the final
response with a one-paragraph recap: files produced, codes per file, and any
`Designer/Developer To Do:` notes the developer must resolve. If several `.txt` worklists are
uploaded at once, process one module at a time (ask which first if unclear). Ask questions only
when the worklist is unreadable or its codes are missing — otherwise build.
