# 15B — The worklist format, and how to build from it

## 1. THE INPUT FILE — `{CODE}_interactives.txt`

PageForge's HTML Generator writes this worklist on every conversion. It lists **only the un-built
interactives** — anything the generator could build automatically is already live in the module
pages and is deliberately omitted.

### File header

```
=====================================
INTERACTIVE REFERENCE — XDLS908
Generated by HTML Generator V2 (Phase 1)
=====================================

TOTAL INTERACTIVES: 65
  Tier 1 (simple static structures): 24 — accordion, flipCard, speechBubble, tabs
  Tier 2 (requires full build): 41
  BUILT AUTOMATICALLY this run: 0  (no work needed — shipped live)
  STILL UN-BUILT (placeholders to develop): 65
  NOTE: this file is the hand-off WORKLIST — it lists ONLY the 65 un-built
  placeholder(s); the 0 BUILT interactive(s) are already live in the HTML and are omitted.
FILES: XDLS908_0_0.html, XDLS908_1_0.html, XDLS908_2_0.html, XDLS908_3_0.html, …

MODE: HAND-OFF (default) — each un-built interactive renders as its REFERENCE CODE box on the
page, with the raw captured content present but COLLAPSED inside it (click the arrow at the right
end of the box to expand/collapse it). The REFERENCE CODE shown at the top of each block below is
the SAME code live in the named File. Search the code (e.g. CODE-INT-NN-SS-type) in that File to
drop the finished widget into place — replacing the whole reference box replaces the hidden raw
content with it.

=====================================
```

`STILL UN-BUILT: N` is the workload and drives the file-split plan (`15A` §6). The per-entry
`REFERENCE CODE:` lines are the anchors; if they are absent, stop and ask for a re-conversion
(`15A` §3). The `MODE:` banner is informational — the hand-off is the generator's default and
needs no toggle. (A worklist from an older generator build may instead read
`MODE: EXTRACT (Phase-1 hand-off)`; if it carries reference codes it is still valid input.)

### One entry, line by line

```
INTERACTIVE 1 of 65
-------------------------------------
REFERENCE CODE:  XDLS908-INT-01-01-dragAndDrop
   ↳ search this exact code in XDLS908_1_0.html to place the finished interactive

File: XDLS908_1_0.html
Placeholder marker: data-cv2-index="1" (the placeholder div to replace)
Activity: 1A
Type: dragAndDrop

Content:
🔴[RED TEXT] [Interactive activity – drag and drop] Answers are placed in the correct columns –
please place outside the table for this activity for learners to drag to the correct place. [/RED TEXT]🔴
┌─── TABLE ───
│ Writing ║ Speaking ║ Visual Communication
│ 🔴[RED TEXT] [Image]  [/RED TEXT]🔴Texting (https://www.istockphoto.com/photo/…) ║ … ║ …
└─── END TABLE ───

-------------------------------------
```

| Line | Meaning | Do you use it? |
|---|---|---|
| `REFERENCE CODE:` | The anchor. Format `{CODE}-INT-{NN}-{SS}-{type}`: `NN` = the page's **position** in the module's page list (overview = `00`), `SS` = running number on that page, `type` = the first detected widget type. **`NN` is a stable index, not part of the filename** — page 2 of `BLL240` is `BLL240_1_1.html` but its codes read `BLL240-INT-02-…`. Never try to derive one from the other; read the `File:` line instead. | **YES — copied verbatim into the section's `data-cv2-ref`.** |
| `File:` | Which module page the marker sits in — named the site-library way, `{CODE}_{lesson}_{part}.html` (`XDLS908_1_0.html`; a sub-paginated or dotted lesson gives `_1_1`, `_2_1`). | Context only. |
| `Placeholder marker:` | The generator's internal index. | Context only — the code is the anchor, not this. |
| `Activity:` | The activity box the interactive belongs to (e.g. `1A`), or `(none — inline component)`. **The page already renders that box — never rebuild it.** | Context only. |
| `Type:` | The widget type(s) detected from the writer's tags. Multiple types joined with ` + ` = the captured region holds several components: build them ALL, in `Content:` order, inside the one section (`15A` §9). The reference code carries only the FIRST type. | **YES — what to build.** |
| `Content:` | The writer's raw captured material, verbatim. | **YES — the build spec.** |

### Reading the `Content:` block

- `🔴[RED TEXT] … [/RED TEXT]🔴` — the writer's red instructions / configuration. **Follow them to
  configure the build, then drop them** — they never appear in output. (A red instruction that is
  a message for a human, not a build instruction, becomes a visible red note per the project's
  Comment & Red Flag Policy — `Writers Note:` for the writer's own note.)
- `[square-bracket tags]` — the writer's structure markers (`[H3]`, `[body]`, `[Image]`,
  `[Tab 1]`, `[back]`, `[Item 2]` …). They say which piece of the widget each line is; they are
  **never** display text (constraint 3).
- `**bold**` = bold; `*italic*` = italic (follow the component file on whether the widget keeps
  it).
- `┌─── TABLE ───` … `└─── END TABLE ───` — a captured data table: one `│`-prefixed line per row,
  `║` between cells, rows top-to-bottom. This is usually the widget's dataset (front/back pairs,
  columns to sort into, quiz options …). Which table shape means which widget is
  `02_DATA_CONTENT_VERIFICATION.md` → Section 06 (Interactive Data Patterns).
- Bare URLs (usually iStock) — the writer's media references; convert per §2 below.

## 2. THE BUILD RULES (fragment-specific)

Everything here is **in addition to** the component files, which own the markup (`15A` §8).

### Declarative HTML only

Te Kura interactives are pure **classes + attributes**; the shared D2L shell script
(`idoc_scripts.js`, loaded by the page) provides all behaviour. **Never** write `<script>`,
`<style>`, an inline style (other than the documented red-note style), or an invented class,
structure or component.

**Exactly two widgets need an extra head include** — and a fragment cannot add head includes, so
**the Page Stitcher injects them automatically** when it places the build:

```html
<script type="text/javascript" src="js/crossword.js"></script>   <!-- class="crossword" -->
<script type="text/javascript" src="js/wordFind.js"></script>    <!-- class="wordFind" -->
```

Build the wrapper correctly and add **one** `Designer/Developer To Do:` note listing the writer's
words/clues so the developer can set up the data file. Other things a fragment cannot supply —
flag them the same way rather than building blind:

- `puzzle` piece sets (central assets) and speech-bubble character art (central image folders);
- `hintSlider`'s `hintCssFile` attribute (it names a CSS file);
- content needing a **body-level** switch (`mathJax`, `reoTranslate`) — a page-level setting;
- any deferred asset or URL the developer must supply during production.

### Build the widget, not the page

The module page already provides the activity box (`<div class="activity interactive"
number="1A">`), the `row`/`col-*` grid, the section headings and the body text outside the
captured region — that is how the "every interactive sits inside an activity wrapper" rule is
already satisfied. The section therefore **starts straight at the widget wrapper** (e.g.
`<div class="dragAndDrop" layout="column">`). Add internal rows/columns **only** where the
component pattern itself requires them. Never emit `<html>`/`<head>`/`<body>`, an activity box,
or the page's outer grid.

### The writer's content is the spec — verbatim

Keep wording, punctuation and macrons (ā ē ī ō ū) exactly as written (constraint 1). Never
"tidy", re-case or re-order the writer's text. Nothing may be silently dropped: anything that
cannot be built is covered by a visible note.

### Media placeholders

Real assets are added by the developer later.

- **iStock image** — `…istockphoto.com/photo/…-gm{ID}-…` or `…/id/{ID}/…` becomes
  `<img class="img-fluid" src="images/iStock-{ID}.jpg" alt="…">`. The **ID is the number
  immediately after `gm`**; for a dual-ID URL `gm{A}-{B}` it is **`A`** (constraint 61). `alt`
  comes from the writer's own description of the item; if the writer gives nothing usable ship
  `alt=""` — never invent, never "stock photo" (constraint 52).
- **Audio** — `<div class="audioButton" audioName="NAME"></div>` (bare name, no path or
  extension) or the full player `<audio preload="none" src="audio/NAME.mp3" class="audioPlayer"
  title="…"></audio>`.
- **Video** — the standard `videoSection ratio ratio-16x9` embed with a
  `youtube-nocookie.com/embed/{ID}` iframe. A Creative Services / Audiovisual video is the Vimeo
  scaffold with the ID left pending plus its `Designer/Developer To Do:` note (constraint 64).
  No TikTok.

### Choosing the type

- **Writer Tag Primacy** — the writer's square-bracket tag picks the component; table headers
  describe the data, not the widget. Build the type named on the `Type:` line.
- `unclassified` → infer the widget from the `Content:` shape using
  `02_DATA_CONTENT_VERIFICATION.md` → Section 06. Two-sided data with no tag defaults to flip
  cards plus a note.
- If the requested type genuinely cannot carry the content, build the **closest documented
  pattern** and open the section with ONE note, in exactly this form:
  `<p style="color: red; font-weight: bold;">Designer/Developer To Do: …</p>`. Use the same form
  for anything else a human must resolve (a missing asset, an ambiguous answer key). A component
  that is not in the component files is **never invented**.

### Answer keys — the load-bearing attributes

Get these right or the interactive does not work. This is a **checklist of what must be correct**;
the COMP file for the component owns the full markup and is the authority.

| Component | The attribute that makes it work | Owned by |
|---|---|---|
| dragAndDrop | `option` pairing (`.drag[option=X]` ↔ `.drop[option=X]`); in **column** layout the option **is** the column number, shared by that column's drops; `layout=` is required | `03_COMP_CORE_INTERACTIVES.md` → COMP_01 |
| multiChoiceQuiz | `value="correct"` on the right `.mcqOption` | → COMP_02 |
| radioQuiz | `answer="true"` / `"false"` on `.radioButtons` (`true||false` = either accepted) | → COMP_02 |
| memoryGame | matching `match="N"` on the two `.memCard`s of a pair | → COMP_04 |
| clickDrop | trigger count **==** content count; in the activity form the paired `number="…"` | `04_COMP_SEGMENTS_OVERLAYS.md` → COMP_07 |
| shapeHover | positional pairing, counts **must** match on both sides | → COMP_08 |
| dropDown / dropQuiz | `answer="1"` (1-based; multi-correct `answer="1 3"`) + `options="A||B||C"` | → COMP_02 |
| selfCheck | `checkOn` + the required `.sCAnswerContainer` sibling | `03_COMP_CORE_INTERACTIVES.md` → COMP_03 |
| typing | `answer="…"` on `.typeInput` (alternates `answer="a||b"`) | → COMP_02 |
| reorder / clickingOrder | `item="N"` sequence (`item="0"` + `blank` = decoy) | → COMP_05 |
| crossword / wordFind | EMPTY wrapper + `crosswordData`/`wordFindData`; wordFind also needs `id="WF"` and a following `<div class="clearDiv"></div>` | → COMP_04 |

`||` is the universal multi-value delimiter (options, alternate answers, word lists). If the
writer marked the answers (red text, an answer column, bold), honour them **exactly**.

### Shuffle, feedback and buttons

- **Shuffle default:** allow shuffling — do **not** add `noShuffle` unless the writer explicitly
  asks. "The items are currently in the correct place" describes the source data; it is not a
  lock request.
- **`autoCheck` only when instant feedback is asked for** — and with `autoCheck` the buttons row
  shrinks to **Reset only** (no undo, no check-answers).
- Per-component button classes differ (`mcqReset`/`mcqAswers` vs `mcqAnswers`, `memGameReset`,
  `cloReset` …). **Copy them from the component file's button table, never from memory.**

### Never emit

The deprecated patterns recorded in the component files — including dragAndDrop
`layout="feedback"` / `layout="mixedContent"`, the standard `randomSelect` variant, TikTok
embeds, `imageZoom` layouts other than `hoverFollow`, and `.alert.teacher` (authoring-only, never
student-facing). A commented-out block in a template source is deprecated or experimental — not a
pattern.

## 3. FAMILY CONVENTIONS STILL APPLY

The module code on the worklist header tells you the family. Where that family has documented
global parameters (`14_SUBJECT_GLOBAL_PARAMETERS.md`) they apply to the interactive too — for
example the WJFUN inline speech-bubble audio button, the WJFUN `[word highlighter]` static
spans, the WJ wrapper-width rule, and the HPE speech-bubble character conventions. Check `14`
whenever the code matches a documented family, exactly as Conversion Mode would.
